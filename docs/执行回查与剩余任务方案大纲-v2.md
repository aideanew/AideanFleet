# 第二部分 · 流程执行逻辑分析（逐模块穿透代码底层）

## 2.1 端到端主链路（intake → scheduler → dispatcher → gate → reviewer）

### 2.1.1 intake：对话指令 → 项目注册 → 三级计划 → DRAFT 任务建册

**证据链**：`fleet/manager/intake.py` 全文（228 行）

**执行逻辑**：

1. `detect_launch_intent(message)`（line 62-85）：用 3 个正则模式匹配"启动新项目"指令。支持 Windows 驱动器路径（`E:\Demo\Project`）和 Linux 绝对路径（`/home/user/project`）。返回 `(pid, workspace)` 或 `None`。
   - **辩证分析**：正则 `[\u4e00-\u9fa5]+` 允许中文项目名，但 `pid = re.sub(r"[^A-Za-z0-9_\-]", "", ...)` 会剥离中文字符。如果用户输入纯中文项目名，`pid` 变成空字符串，后续 `start_project` 抛 `ValueError`。**这是合理的设计约束**——项目 ID 必须是 ASCII，但前端没有提示这个限制。

2. `_allowed_roots()`（line 26-42）：从 `.env` basic 段读 `allowed_roots`，回退到环境变量 `FLEET_ALLOWED_ROOTS`。
   - **问题**：`.env.example` 中 `FLEET_ALLOWED_ROOTS=${FLEET_ALLOWED_ROOTS}` 是自引用占位符。如果用户直接复制 `.env.example` 为 `.env` 且未设环境变量，`_allowed_roots()` 返回空列表，`start_project` 抛 `ValueError("ALLOWED_ROOTS 未配置")`。**已在 `.env` 手动修正为 `/root`，但 `.env.example` 未改**。

3. `start_project(pid, name, workspace, requirements)`（line 113-228）：
   - 注册项目到 DB（`db.create_project`）
   - **幂等防护**：如果项目已有任务，返回 `already=True`，不重复建任务（line 165-169）
   - 生成三级计划模板（`_plan_templates`）：技术设计（1 任务）→ 核心实现（2 并行任务）→ 测试验收（2 任务），共 5 个 DRAFT 任务
   - 阶段间串行依赖：后阶段所有任务依赖前阶段所有任务的 task_id（`dependencies=list(prev_stage_ids)`）
   - 返回 dict：`{project, workspace, stages, tasks, already, created}`——**注意无 `project_id` 键**（此前模拟脚本曾因 `result["project_id"]` 报 KeyError）

**结论**：intake 模块逻辑自洽，幂等防护有效。主要风险在 `.env.example` 的占位符问题。

### 2.1.2 scheduler：DRAFT 收编 → READY 判定 → 派工推进

**证据链**：`fleet/manager/scheduler.py` 全文（175 行）

**执行逻辑**：

1. `ControlBus`（line 36-92）：内存总线，`mode`（auto/step）+ `confirms` 队列。线程安全（`threading.Lock`）。
   - **辩证分析**：`ControlBus` 是纯内存的，服务重启后模式丢失。`server.py:51-53` 的 `bus` 初始化从 `.env` 读 `FLEET_SCHEDULER_MODE` 恢复，但 confirms 队列不可恢复——step 模式下重启会丢失未消费的确认。**这是合理的设计**：确认是即时操作，不需要持久化。

2. `collect_drafts(project_id)`（line 95-110）：把 DRAFT 任务迁移到 ASSIGNED。**不判依赖**——READY 判定由 `dag.get_ready_tasks` 负责。
   - **辩证分析**：这意味着所有 DRAFT 任务都会变成 ASSIGNED，即使依赖未满足。ASSIGNED 但不可派工的任务会停在队列里等依赖完成。**这是正确的设计**——状态迁移与可派工性是两个正交概念。

3. `schedule_once(project_id, once=False)`（line 132-175）：
   - auto 模式：派完所有 READY → 把所有 SUBMITTED 推进机器门到终态
   - step 模式（once=True）：优先推进 SUBMITTED（机器门），否则派一个 READY
   - `_safe_dispatch` 包装：单任务异常落 BLOCKED，不杀调度循环（line 112-127）

4. `run_loop(bus, ...)`（line 177-175）：常驻循环，0.5s 一拍。step 模式下无 confirm 就 `asyncio.sleep` 挂起。
   - **性能分析**：0.5s 定拍意味着任务完成到下一个任务派工之间最多 0.5s 延迟。对于 LLM 调用（秒级到分钟级），这个延迟可忽略。但如果未来需要高吞吐（多项目并发），0.5s 定拍会成为瓶颈——可改为事件驱动。

**结论**：scheduler 逻辑健壮，异常隔离有效。`_safe_dispatch` 是关键防线——它确保单个任务派工失败不会杀死整个调度循环。

### 2.1.3 dispatcher：ASSIGNED → DOING → SUBMITTED（含模型链重试）

**证据链**：`fleet/manager/dispatcher.py` 全文（335 行）

**执行逻辑**：

1. `dispatch(task_id)`（line 168-300）：
   - 断点恢复：DOING 幂等返回（line 183-185），SUBMITTED 幂等返回（line 187-190）
   - DRAFT → ASSIGNED → 补路径 + 拍基线快照 → ASSIGNED → DOING → 调适配器 → DOING → SUBMITTED
   - `ensure_paths`（line 50-64）：补齐 report_path / evidence_path / baseline_path，写回 DB
   - `capture_baseline`（调用 `verify.capture_baseline`）：派工前拍工作区快照，事后扫"改了什么"

2. `_adapter_for(task)`（line 66-87）：优先 task.adapter 字段，否则从 roles 配置查 assignee 对应的 adapter。解析后写回 DB（line 78-82）。
   - **辩证分析**：写回 DB 是 P-008 修复（DB adapter 列恒为空的问题）。但 `try/except Exception: pass` 静默吞错——如果 DB 写失败，下次派工会重新解析，不会出错但会浪费一次解析。**可接受**。

3. `_run_with_chain`（line 113-175）：按角色模型链调用适配器。
   - 软失败（429/超时）：等 10 秒重试，最多 10 次
   - 硬失败（401/工具失败）：立即换下一个模型
   - **孤儿切换守卫**（line 136-153）：每次 adapter.run 后检查任务是否被外部升级为 BLOCKED/ESCALATED。如果是，立即中止模型链。**这是 P-008 实测修复**——BLOCKED 后 26 分钟仍在切模型的 bug。
   - `run_context`（line 128-131）：线程局部上下文，供 `registry.begin()` 登记进程归属。

4. `run_to_completion(task_id)`（line 302-335）：dispatch → review → rework 循环，最多 4 轮。
   - PASS/PARTIAL → 从报告提炼项目记忆（`project_memory.distill_from_report`）
   - BLOCKED → 停
   - REWORK → 交 `rework_manager.handle_rework`，ASSIGNED 则继续下一轮

**结论**：dispatcher 是整个流程的核心，逻辑复杂但防御性编程到位。断点恢复、孤儿守卫、模型链重试三层保护确保异常路径不丢失状态。

### 2.1.4 verify（Machine Gate）：verify_cmd + 禁改扫描 + 证据存在性 + 路径污染守卫

**证据链**：`fleet/gates/verify.py` 全文（311 行）

**执行逻辑**：

1. `run_gate(task)`（line 215-280）：固定顺序执行 4 项检查 + 1 项守卫：
   - ① workspace 存在性 → 不存在 = fatal BLOCKED
   - ② 改动文件扫描（基线快照 diff / git status 兜底）→ 无基线且非 git 仓库 = fatal BLOCKED
   - ③ verify_cmd 执行 → exit_code ≠ 0 = REWORK
   - ④ 禁改文件扫描（forbidden_files）+ 白名单越界（allowed_files）
   - ⑤ 路径污染守卫（`flattened_path_dirs`）：检测"压扁路径"形态目录（如 `srcfeaturestablestore`）
   - ⑥ 证据文件存在性（evidence_path 非空且存在）

2. `changed_files_of(task)`（line 167-185）：优先用基线快照 diff，退化用 `git status --porcelain`，都没有则 `source="none"` → fatal。
   - **辩证分析**：基线快照方式比 git 更精确（能检测到非 git 仓库的改动），但快照只记录 mtime_ns 和 size——如果文件被修改但大小恰好不变且 mtime 精度不够，可能漏检。**实际风险极低**：文本编辑几乎不可能保持文件大小完全一致。

3. `flattened_path_dirs`（line 232-262）：贪心分解目录名为已知路径段。词表 `_FLATTEN_SEGMENTS` 有 44 个段。
   - **辩证分析**：这是 2026-09-17 Test09171131 事故的专项修复。如果执行体创建了 `srcfeaturestablestore` 这样的压扁目录，说明它把绝对路径当单层目录名创建了。守卫只检新增目录形态，不惩罚合法产物。**设计合理**，但词表是硬编码的——如果未来有新的路径段不在词表里，会漏检。建议改为"目录名长度 > 20 且不含分隔符"的启发式判断。

**结论**：Machine Gate 是"不可被 LLM 改判"的硬门控，设计严谨。`baseline_source="none"` 的 fatal 处理确保了"无法证明改了什么"的任务不会被放行。

### 2.1.5 reviewer：机器门 → 审查角色 → 终态

**证据链**：`fleet/manager/reviewer.py` 全文（212 行）

**执行逻辑**：

1. `review(task_id)`（line 99-212）：
   - 第一步：`verify.run_gate(task)` → 机器门结果
   - 机器门 fatal → BLOCKED（不发 gate:pass/gate:fail 事件，只发 task:blocked）
   - 机器门失败 → `_rework`（rework_count +1，>3 次 ESCALATED）
   - 第二步：机器门通过 → 调审查角色（`router.call`）→ `determine_verdict` 解析回执
   - 回执非法（不是四值之一）→ BLOCKED（"绝不默认放行为 PASS"）
   - 第三步：PASS → DONE，PARTIAL → PARTIAL，REWORK → `_rework`，BLOCKED → BLOCKED

2. `determine_verdict(text)`（line 62-84）：三级解析——JSON verdict 字段 → `VERDICT: X` 行 → 全文唯一四值词。两个不同判定词 = 歧义 = None = BLOCKED。
   - **辩证分析**：这个解析器非常严格，但依赖正则。如果审查角色返回的文本中碰巧包含了两个判定词（如"这个任务 PASS 了，没有 REWORK 必要"），会被判为歧义 → BLOCKED。**这是安全侧的过度保守**——宁可阻塞也不误放行，符合"Machine Gate 权威高于 Agent 自述"的原则。

**结论**：reviewer 的"机器门优先 + 审查角色补充"两层架构确保了质量门控的不可绕过性。`determine_verdict` 的严格解析是安全正面的过度保守。

## 2.2 状态机一致性核验

**证据链**：`fleet/core/state_machine.py` 全文（92 行）

**核验结果**：

- 10 个状态：DRAFT / ASSIGNED / DOING / SUBMITTED / REVIEWING / DONE / PARTIAL / REWORK / BLOCKED / ESCALATED
- 迁移表与 `docs/契约/任务状态机.md` 一致（逐条比对 TRANSITIONS dict）
- `REWORK_ESCALATE_THRESHOLD = 3`：返工 > 3 次 → ESCALATED
- 3 个终态：DONE / PARTIAL / ESCALATED（无出边）
- `assert_transition` 在写 DB 之前调用——非法迁移抛异常且不落库

**结论**：状态机是纯函数模块，不碰 DB、不写事件，设计干净。所有状态迁移通过 `db.transition_and_log` 统一落库+发事件，保证了原子性。

## 2.3 DAG 依赖引擎

**证据链**：`fleet/manager/dag.py` 全文（177 行）

**执行逻辑**：

- `get_ready_tasks`：ASSIGNED + 依赖全 DONE + 与 DOING 任务无文件范围冲突
- 文件范围冲突：`_ranges_conflict` 用 fnmatch 交叉匹配 allowed_files 模式
- `task:deferred` 事件去重：`(project_id, task_id)` 键，同一冲突签名只发一次
- 返工链语义：`_successor_chain_done` 检查依赖任务是否有 DONE 的后继返工任务（`{dep_id}-R*`）

**辩证分析**：文件范围冲突检测用 fnmatch 交叉匹配，对于 `*` 模式（无限制白名单）会与任何模式冲突——这意味着两个白名单为空的任务不能并行执行。**这是保守但安全的设计**：如果不知道任务会改什么文件，就不应该并行跑。但这也意味着默认模板中"核心实现"阶段的两个任务（be-1 和 fe-1）如果都不设 allowed_files，会被判定为冲突而串行执行。**需检查 intake 模板**：

回看 `intake._plan_templates`（line 118-200）：所有任务的 `allowed_files=""`——空字符串。`dag._allowed_patterns` 对空字符串返回 `["*"]`。因此"核心实现"阶段的 be-1 和 fe-1 会被判定为文件范围冲突，**实际串行执行而非并行**。

**这是一个实际影响性能的问题**：设计意图是"阶段内并行"，但空 allowed_files 导致 DAG 判定冲突，退化为串行。

## 3.5 dist/ 构建产物不入 git 的问题

- `git ls-files fleet/console/dist/` → 空

- 方案丙：在 `server.py` 启动时检测 `dist/` 是否为空，为空则打印警告并引导构建。**最小成本**。

# 第四部分 · 辩证问题清单（正面 / 反面 / 裁决）

## 4.1 FakeAdapter 不写产物导致 Machine Gate 必然失败

| 面 | 论点 |
|---|---|
| 正面 | FakeAdapter 是测试适配器，`run()` 只 `sleep(0.1)` 返回文本，不写文件。Machine Gate 的 `verify_cmd` 检查文件存在性，必然 exit_code=1 → REWORK。**这是设计意图**：测试适配器不应该通过质量门控。 |
| 反面 | 如果用 FakeAdapter 做端到端流程验证（如模拟五子棋项目），整个流程会在 Machine Gate 处卡住，无法到达 DONE。模拟只能验证 intake → scheduler → dispatcher → SUBMITTED 链路，无法验证 review → DONE。 |
| 裁决 | **设计正确，无需修改**。FakeAdapter 的职责是测试调度/重试/通知逻辑，不是验证端到端交付。要验证完整流程，需要一个"真实适配器"（如 OpenCode/ClaudeCode）或一个"MockWriteAdapter"（在 run() 中按 verify_cmd 创建文件）。 |

## 4.2 "核心实现"阶段任务实际串行而非并行

| 面 | 论点 |
|---|---|
| 正面 | `intake._plan_templates` 中所有任务的 `allowed_files=""`。`dag._allowed_patterns` 对空字符串返回 `["*"]`。`_ranges_conflict(["*"], ["*"])` 返回 True。因此同阶段任务被判定为文件范围冲突，串行执行。 |
| 反面 | 设计意图是"阶段内并行"（`intake.py` docstring："阶段内任务并行（无互相依赖），阶段间串行"）。DAG 的文件冲突检测是为了防止并行任务写同一文件，但空 allowed_files 导致过度保守。 |
| 裁决 | **应修复**。在 `_plan_templates` 中为每个任务设定合理的 `allowed_files`（如 be-1 设 `src/**,docs/design.md`，fe-1 设 `index.html,src/components/**`），让 DAG 能正确判断无冲突。或者在 `dag._ranges_conflict` 中对双方都是 `["*"]` 的情况做特殊处理（不判定为冲突，但发 warning 事件）。 |

## 4.3 `.env.example` 自引用占位符

| 面 | 论点 |
|---|---|
| 正面 | `FLEET_ALLOWED_ROOTS=${FLEET_ALLOWED_ROOTS}` 是占位符写法，提示用户"这个值应该从环境变量取"。 |
| 反面 | `config.py` 的 `.env` 解析不会展开 `${VAR}`（它不是 shell）。`_allowed_roots()` 读到字面量 `${FLEET_ALLOWED_ROOTS}`，`split(",")` 得到 `["${FLEET_ALLOWED_ROOTS}"]`，`_workspace_allowed` 用这个字符串做路径前缀匹配，永远不匹配 → `start_project` 抛 `ValueError`。 |
| 裁决 | **应修复**。`.env.example` 应改为 `FLEET_ALLOWED_ROOTS=/root` 或注释说明"请改为你的实际路径"。`${VAR}` 语法在 `.env` 文件中无意义且有害。 |

## 4.4 `dist/` 不入 git vs 开箱即用

| 面 | 论点 |
|---|---|
| 正面 | `.gitignore` 排除 `dist/` 是前端项目惯例，避免构建产物污染版本库。 |
| 反面 | 克隆仓库后控制台不可用，必须先安装 Node.js + pnpm 并构建。违反"初中生能完成"原则。 |
| 裁决 | **折中方案**：在 `server.py` 启动时检测 `dist/` 是否为空，为空则打印醒目警告 + 构建指引。同时在 Makefile 中提供 `make build-web` 一键命令。不把 `dist/` 纳入 git（保持惯例），但降低构建门槛。 |

## 4.5 `on_event("startup")` 弃用

| 面 | 论点 |
|---|---|
| 正面 | FastAPI 的 `@app.on_event("startup")` 已弃用，推荐使用 `lifespan` 事件处理器。`DeprecationWarning` 实测触发。 |
| 反面 | 功能仍然正常，只是警告。迁移到 `lifespan` 需要重构 `_on_startup` 函数为 `async` 上下文管理器，改动量不小。 |
| 裁决 | **应修复但非紧急**。`on_event` 在可预见的未来仍可用（FastAPI 兼容性承诺）。但在 P4 技术债清理阶段应迁移，避免未来升级 FastAPI 时破裂。 |

# 第七部分 · 高性能 / 高拓展性设计要点

## 7.1 高性能（当前 → 目标）

| 维度 | 当前 | 目标 | 改造点 |
|---|---|---|---|
| 事件流查询 | 全量读取 + 内存过滤 | 游标式 `WHERE seq > ?` | P2-A |
| WS 广播 | 全连接遍历 | 项目级过滤（已部分实现） | P2-B |
| 调度循环 | 0.5s 定拍 | 事件驱动（任务完成即触发下一轮） | 未来（当前 0.5s 足够） |
| 前端列表 | 全量渲染 | 虚拟滚动 | P2-C |
| DAG 冲突检测 | fnmatch 交叉匹配 | 按目录前缀分组（减少 O(n²) 比较） | 未来（当前任务数 <20 足够） |

## 7.2 高拓展性（新增能力的成本）

| 新增能力 | 改动范围 | 成本 |
|---|---|---|
| 新适配器 | 新建 `fleet/executors/<name>.py` + `register_adapter` + `.env` 角色配置 | 1 文件 + 配置 |
| 新页面 | 新建 `pages/XxxPage.vue` + `router/index.ts` 加路由 + `stores/` 加 store | 2-3 文件 |
| 新 API 路由 | `server.py` 加 `@app.get/post` + `api/client.ts` 加方法 | 2 文件 |
| 新状态 | `state_machine.py` 加状态 + 迁移表 + 契约文档 | 1 文件 + 文档 |
| 新门控检查 | `verify.py::run_gate` 加检查项 | 1 函数 |
| 新通知触发器 | `notify/triggers.py` 加映射 + `.env` 加键 | 1 文件 + 配置 |

## 7.3 最小原子化原则

每个原子任务满足：
1. **可独立验收**：有明确的验证命令或文件检查
2. **可独立提交**：改动 ≤3 个文件（除非是移动文件）
3. **可独立回滚**：git revert 单个 commit 不破坏其他功能
4. **无隐含依赖**：除标注的联动文件外，不影响其他模块
