## 3.1 端到端主链路（实测走通的唯一样本）

```text
用户/启动器
  │  POST /api/session {project} ──────────► 签发 64-bit hex token（内存表，TTL 3600s）
  ▼
控制台 (127.0.0.1:5000, FastAPI, 单进程)
  ├─ 中间件 session_gate：非豁免 /api/* 无 token → 401
  ├─ GET /api/plan ──► core/plan.snapshot + db 聚合 ──► 三级大纲 + progress
  ├─ GET /api/events?since=N ──► core/events.read(since=N)   ← ★ P1-5 性能热点
  ├─ POST /tasks/{id}/dispatch ──► manager.dispatcher.run_to_completion
  └─ WS /ws ──► _event_pump（1 拍/秒）──► 7 种 type 广播
                                   │
        ┌──────────────────────────┘
        ▼
manager.dispatcher.run_to_completion(task_id)
  1) db.get_task → 状态合法性校验（state_machine.assert_transition）
  2) DRAFT→ASSIGNED→DOING 迁移 + events.append（每步）
  3) context_budget.assemble_prompt(system + memory_header + 任务说明 + 裁剪后上下文)
       → events.append("prompt:assembled") + ("budget:check" / 可能 "budget:exceeded")
  4) executors.<adapter>.run(prompt, workdir, model, timeout)
       → 子进程树安全执行（run_subprocess_tree_safe，超时杀整树）
       → data/evidence/<task>/attempt-N.log（原文不截尾，AgentResult.output 截尾 2000）
  5) gates/verify.run：
       ├─ verify_cmd exit_code ≠ 0 ──► FAIL
       ├─ forbidden_files 被改 ──► FAIL
       └─ expected_files 缺失 ──► FAIL
       （致命异常 → fatal=True → BLOCKED，而非 REWORK）
  6) reviewer：机器门 FAIL 直接 REWORK（不调 LLM）；PASS 才让审查角色出四值之一
  7) REWORK → rework_manager：rework_count+1；>3 → ESCALATED（等人工）
  8) 终态 DONE/PARTIAL → plan.sync_from_db（单向）→ core/memory.distill_from_report
```

## 3.3 三个真实性能热点（代码级证据）

1. **`events.read()` 是 O(N) 全文件解析**
   `fleet/core/events.py:138-153` → 调 `_iter_rows()`（同文件 64-77 行）→ `for line in handle` 把**每一行都 json.loads** 后再按 `seq > since` 过滤。
   调用者：① 事件泵**每秒 1 次**（`server.py:201`）；② 每个客户端 `GET /api/events` 一次；③ `current_cursor(project)` 又扫一遍（`events.py:160`）。
   `max_seq()` 有 size 缓存（83-90 行），但 `read()` **完全无缓存、无字节偏移游标**。
   当前 1059 行无感；本系统的设计前提是「长跑自治项目、每个状态迁移写一条事件」→ 量级到 10^5~10^6 行时，每拍每客户端全量解析。

2. **进度聚合在泵内对每个项目重算**
   `server.py:206 / 215` 每条事件后都 `broadcast(progress, **_progress_of(project))`；`_progress_of` 走 `plan.snapshot` + DB 聚合，无按 (plan_mtime, max_seq) 的缓存。

3. **广播无背压与死连接剔除**
   `broadcast()` 对 `_connections` 全量 `send_text`；对端 TCP 假死时异常被 `except: pass`（`server.py:220-221`）吞掉，不摘除连接——与 P3-B 的 e2e 顺序依赖失败机理同源。

## 阶段 P2 · 高性能改造（可观测 + 吞吐）

### P2-A 事件流读取改为游标式（核心性能项）

#### P2-A-1 稀疏索引
- **P2-A-1-1** `fleet/core/events.py` 新增 `_IDX` 机制：每 **256 行** 记录 `(seq, byte_offset)`，落 `data/.events.idx`（JSON）

#### P2-A-2 `read()` 快路径
- **P2-A-2-1** `read(since=N)`：查索引定位到 ≤N 的最近档 → `f.seek(offset)` → 只解析尾部

#### P2-A-3 事件泵改尾随

- **P2-A-3-2** 文件被截断（归档/轮转）→ `size < offset` 时回落到索引重建路径
- **P2-A-3-3** 归档锚点事件（`rel:archived`）后 seq 连续语义不得破坏（`verify_continuity` 保持可用）

#### P2-A-4 基准与门禁

| 事件泵 | 每秒全量扫 + 每项目重算进度 | 尾随读 + 双键缓存 | `stat` 短路 + `(mtime, seq)` 缓存 | 空转 CPU <1% |
| WS 广播 | 同步全量 send，异常吞掉 | 每连接队列 + 死连接剔除 | `Queue(maxsize=1000)` + 失败计数 | 10 客户端接入无延迟劣化 |
| DB | 无索引 | 双复合索引 | `CREATE INDEX IF NOT EXISTS` | 万级任务列表查询 <50ms |
| 前端 | 每事件一次重渲染 | 帧批处理 | 16ms 窗口合并 | 事件风暴下 FPS ≥50 |
| 首屏 | 未测 | <2s | chunk 预算 + 虚拟滚动 | Lighthouse/perf timing 留证 |

## 7.3 最小原子化原则（本大纲的遵守方式）

1. **一个四级项 = 一个可验证动作**：改一个文件的一处 / 跑一条命令 / 写一个用例。
2. **每项自带验证命令**：不写「优化事件读取」，而写「`read(since=99900)` 在 10 万行下 <50ms」。
3. **契约先于实现**：任何字段级变更，`docs/契约/` 的改动作为独立原子项排在实现项之前。
4. **删除必先证明零引用**：P4-A 全部条目以 grep 零命中为前置。
5. **不合并「改代码」与「留证据」**：evidence 文件是独立原子项，避免「做完忘记留痕」重演（本轮已见 3 处证据与实际不符）。
