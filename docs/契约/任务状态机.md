## 1. 状态定义（10 个，名称冻结）

| 状态 | 中文 | 含义 | 终态 |
|---|---|---|---|
| `DRAFT` | 草稿 | 任务已建立，字段已填，尚未派工 | 否 |
| `ASSIGNED` | 已派工 | 已确定 assignee/reviewer 并完成派工动作 | 否 |
| `DOING` | 执行中 | 执行体适配器已被调用，工作正在进行 | 否 |
| `SUBMITTED` | 已提交 | 执行体返回六节报告与证据，等待机器门 | 否 |
| `REVIEWING` | 审查中 | 机器门已通过，已转交审查角色 | 否 |
| `DONE` | 完成 | 机器门 PASS + 审查 PASS | **是** |
| `PARTIAL` | 部分完成 | 审查 PARTIAL，可交付但有缺口，本轮收口 | **是** |
| `REWORK` | 返工中 | 需要重做（机器门失败或审查 REWORK） | 否 |
| `BLOCKED` | 阻塞 | 外部依赖/网关/额度/证据不足，非实现失败 | 否 |
| `ESCALATED` | 升级 | 返工次数超过上限，必须人工介入 | **是** |

**终态**：`DONE`、`PARTIAL`、`ESCALATED` —— 无任何出边。

## 2. 合法迁移表（唯一权威，新增迁移必须改本表 + 状态机实现 + 单测）

| # | from | to | 触发者 | 触发条件 | 副作用 |
|---|---|---|---|---|---|
| 1 | `DRAFT` | `ASSIGNED` | Manager(dispatcher) | 派工开始，assignee/reviewer 非空 | 写 `tasks.updated_at`；事件 `task:assigned`；plan 重写 |
| 2 | `ASSIGNED` | `DOING` | Manager(dispatcher) | 适配器解析成功且已调用 | 事件 `task:doing` |
| 3 | `ASSIGNED` | `BLOCKED` | Manager(dispatcher) | 适配器不可用 / 网关离线 | 事件 `task:blocked`（附失败原因） |
| 4 | `DOING` | `SUBMITTED` | Manager(dispatcher) | 已收六节报告 + 证据文件 | 事件 `task:submitted` |
| 5 | `DOING` | `BLOCKED` | Manager(dispatcher) | 外部依赖不可用；或回执缺节/未能取得回执 | 事件 `task:blocked` |
| 6 | `SUBMITTED` | `REVIEWING` | Manager(reviewer) | **机器门已执行完毕**（进入判别阶段，PASS 与失败都要进，失败时紧接着走迁移 #10） | 事件 `task:reviewing` |
| 7 | `SUBMITTED` | `BLOCKED` | Manager(reviewer) | 机器门本身无法执行（如 workspace 缺失） | 事件 `task:blocked` |
| 8 | `REVIEWING` | `DONE` | 审查角色 | 审查判定 = `PASS` | 事件 `task:done` |
| 9 | `REVIEWING` | `PARTIAL` | 审查角色 | 审查判定 = `PARTIAL` | 事件 `task:partial` |
| 10 | `REVIEWING` | `REWORK` | 审查角色 | 审查判定 = `REWORK`，或机器门失败强制改判 | `rework_count += 1`；事件 `task:rework` |
| 11 | `REVIEWING` | `BLOCKED` | 审查角色 | 审查判定 = `BLOCKED`，或审查回执非法值 | 事件 `task:blocked` |
| 12 | `REWORK` | `ASSIGNED` | Manager(dispatcher) | `rework_count <= 3` | 事件 `task:rework_dispatch`（返工意见并入 detail） |
| 13 | `REWORK` | `ESCALATED` | Manager(dispatcher/reviewer) | `rework_count > 3` | 事件 `task:escalated` |
| 14 | `BLOCKED` | `ASSIGNED` | Manager(dispatcher) | 依赖已真实解除（需附证据；人工放行走 `/api/control/confirm`） | 事件 `task:blocked_release`（依赖解除类仍可为 `task:reassigned`） |

### 2.1 明确禁止的迁移（举例，非穷举）

- `DRAFT → DONE`、`DRAFT → DOING`、`DRAFT → SUBMITTED`
- `ASSIGNED → SUBMITTED`、`ASSIGNED → DONE`、`ASSIGNED → REVIEWING`
- `DOING → DONE`、`DOING → REVIEWING`、`DOING → REWORK`
- `SUBMITTED → DONE`、`SUBMITTED → REWORK`（必须先经 `REVIEWING`）
- 任何终态（`DONE` / `PARTIAL` / `ESCALATED`）的出边
- `REWORK → DOING`（必须回到 `ASSIGNED`，以保证重新派工被记录）

### 2.2 非法迁移的处置（硬规则）

1. 抛 `InvalidTransition`（`fleet/core/state_machine.py`）。
2. **不得落库**：`UPDATE tasks` 与 `events.jsonl` 追加都必须发生在校验之后。
3. 控制台 API 收到 `InvalidTransition` → HTTP `409`，body `{"ok": false, "reason": "invalid_transition"}`。

## 3. 返工计数与升级（ESCALATED）

```text
reviewer 判定 REWORK 或机器门失败
        ↓
rework_count += 1          （由 state_machine.resolve_rework_target 统一计算）
        ↓
rework_count <= 3  → REWORK → ASSIGNED
rework_count  > 3  → REWORK → ESCALATED   （第 4 次返工即升级）
```

- 边界口径：**"REWORK 次数 > 3 → ESCALATED"**，即第 1/2/3 次返工可继续自动重派，第 4 次升级。
- `ESCALATED` 必须由人工处置；系统不得自动把 `ESCALATED` 改回 `ASSIGNED`。
- `rework_count` 字段名与语义见 `任务进度表字段.md`。

### 3.1 db 层实现语义（v1.1 复核确认，与 §2 表等价）

实现中 `fleet/core/db.py::bump_rework` 把 "REVIEWING → REWORK"与 "REWORK → ASSIGNED/ESCALATED"
合并为**一次落库**：`rework_count += 1` 后直接落 `resolve_rework_target(count)`
（≤3 → `ASSIGNED`，>3 → `ESCALATED`），`REWORK` 仅作为 `review_status` 存在、不作为中间落库态。
事件流仍保持与 §2 表一致的语义：`task:rework`（或 `task:escalated`）由 reviewer 发出，
`task:rework_dispatch` 由返工重派发出——外部观察者看到的事件序列与 §2 表逐条对应。

## 4. 与其他文档口径的融合映射（工作包 §7-2 要求的融合口径）

### 4.1 `初始设计/核心2.md` 的"执行状态 1~4 / 审查状态 1~4"

用户早期设计使用数字枚举，本契约使用字符串枚举（机器可读、可 grep、事件流可读）。映射关系：

| 核心2.md 数字 | 核心2.md 含义 | 本契约 `exec_status` | 本契约 `review_status` |
|---|---|---|---|
| 执行状态 1 | 等待 | `DRAFT` / `ASSIGNED` / `REWORK` / `BLOCKED` | `PENDING` |
| 执行状态 2 | 执行中 | `DOING` | `PENDING` |
| 执行状态 3 | 执行完成 | `SUBMITTED` / `REVIEWING` / `DONE` / `PARTIAL` | 见右列 |
| 审查状态 1 | 等待 | — | `PENDING` |
| 审查状态 2 | 审查中 | `REVIEWING` | `REVIEWING` |
| 审查状态 3 | 审查通过 | `DONE` | `PASS` |
| 审查状态 4 | 审查不通过 | `REWORK` | `REWORK` |

补充：早期设计的"审查不通过"无法区分"该重做"与"被外部阻塞"，本契约拆为 `REWORK`（重做）与 `BLOCKED`（阻塞）两值；`PARTIAL`（部分通过）为新增值，来源见 `docs/启动Hermes派工2(英文版).txt` §10。

### 4.2 `docs/启动Hermes派工2(英文版).txt` §6 状态机

该文档列出的迁移与本契约**逐条对齐**，唯一差异是它额外出现 `FAILED`：

| 该文档 | 本契约 | 理由 |
|---|---|---|
| `FAILED -> ASSIGNED` | `REWORK -> ASSIGNED`（实现失败）或 `BLOCKED -> ASSIGNED`（依赖失败） | 本工作包 §9.1-1 未定义 `FAILED`；"实现失败"归 `REWORK`，"非实现原因失败"归 `BLOCKED`，与 `初始设计/d7.md` "BLOCKED 和 FAILED 必须区分" 的意图一致且更易机器判定 |
| `BLOCKED -> ASSIGNED`（依赖解除后） | 一致（迁移 #14） | — |

## 5. 迁移的持久化与事件顺序（不可颠倒）

每次迁移必须按以下顺序执行，任一步失败即整体回滚（SQLite 事务）且不追加事件：

```text
1. state_machine.assert_transition(from, to)   # 不合法 → InvalidTransition，直接抛
2. db.transition(task_id, to)                  # 单事务内 UPDATE tasks
3. events.append(...)                          # 追加一行 JSON，永不修改历史行
4. plan.update_task(...)                       # 原子重写 plan.json
```

事件 `seq` 单调递增，事件字段见 `控制台API.md` §3。
