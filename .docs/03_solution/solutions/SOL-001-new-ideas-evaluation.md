# SOL-001：7 个新设想评估

> 评估日期：2026-09-24
> 评估原则：性能最优 + 初中生都能完成开发的最简流程
> 评估方法：双向钢人论证（先尽力为设想辩护，再尽力反驳，最后裁决）
> 关联 ADR：ADR-024 ~ ADR-030

---

## 设想 1：Prompt 模板文件系统（变量化）

**设想内容**：建立 `fleet/prompts/{role}/` 目录，每个角色一套 Markdown 模板，内含 `{{variable}}` 占位符，派工时自动填充任务上下文。

### 钢人正方
- 当前 prompt 散落在 intake.py 和 dispatcher.py 的字符串拼接里，不可复用、不可版本管理
- 模板化后非程序员也能编辑 prompt（改 Markdown 即可），符合"初中生可完成"原则
- 新角色上线只需加一个 .md 文件，零代码改动

### 钢人反方
- 引入模板引擎 = 新依赖，Python 原生 `str.replace` 就够，不需要 Jinja2
- 当前角色只有 3 种（Manager/Executor/Reviewer），prompt 变化频率低，过度工程化
- 模板变量如果类型不明确，初中生会填错，反而增加调试成本

### 裁决：**采纳（简化版）**
- 用 `fleet/prompts/{role}.md` 单文件，Python `str.format()` 填充
- 不引入 Jinja2 或任何模板引擎
- 变量名全部中文直白命名（`{任务描述}`、`{验收标准}`）
- ADR-024 记录此决策

## 设想 2：本地 Skills 系统（项目级）

**设想内容**：类似 Claude Code 的 skills 机制，项目可以定义 `.fleet/skills/` 目录，放置可复用的技能文件（如"创建API"、"写测试"），执行体加载后按技能执行。

### 钢人正方
- 技能复用减少重复 prompt，长期提升执行体输出质量
- 技能文件可以包含检查清单，自动约束执行体行为

### 钢人反方
- Skills 系统 = 注册表 + 加载器 + 发现机制 + 版本管理，这是框架级复杂度
- 当前执行体是外部 CLI（opencode/codex/claude），它们自带 prompt 能力，项目侧再加一层 skills 会产生语义冲突
- "初中生都能完成"原则要求：每加一层抽象必须有 10 倍收益，skills 系统的收益不足以支撑其复杂度
- Phase 2 目标是正确性优先，不是扩展性

### 裁决：**缓行（Phase 3 再评估）**
- 当前用 `docs/执行体/` 下的 Markdown 指导文件代替（已有机制）
- 等执行体适配层稳定、角色种类超过 5 种后再评估
- ADR-025 记录此决策

## 设想 3：Redis 替代 SQLite 管理任务/状态

**设想内容**：用 Redis 替代 SQLite 做任务状态存储，利用 Redis 的内存性能和 pub/sub 能力实现实时通知。

### 钢人正方
- Redis 内存性能远超 SQLite 磁盘 I/O
- pub/sub 天然支持 WebSocket 实时推送
- Redis 数据结构丰富（List 做队列、Hash 做状态、Sorted Set 做优先级）

### 钢人反方
- **致命**：引入 Redis = 新增外部服务依赖，违反项目铁律"零外部服务依赖"
- "初中生都能完成"：安装 Redis + 配置 + 维护是系统管理员级别操作
- SQLite 单文件、零配置、ACID 事务，在 AideanFleet 的并发量级（单机几十个任务）下性能完全够用
- 当前 events.jsonl 的 append-only 模型无法用 Redis 替代（Redis 是内存数据库，宕机丢数据）
- WebSocket 实时推送已通过内存消息队列 + asyncio 实现，不需要 Redis pub/sub

### 裁决：**拒绝**
- SQLite + JSONL 双持久化方案不变
- 性能瓶颈如真出现，先优化 SQLite（WAL 模式、索引、批量写），再考虑换存储
- ADR-026 记录此决策

## 设想 4：自动安装 CLI 执行体（从固定源）

**设想内容**：首次使用时自动检测并安装所需 CLI 执行体（opencode、codex、claude 等），从固定 URL 拉取。

### 钢人正方
- 降低上手门槛，用户不需要手动安装每个 CLI
- 固定源保证版本一致性

### 钢人反方
- 自动安装软件涉及：平台检测（macOS/Linux/Windows）、架构检测（x86/arm）、版本管理、权限处理、签名验证——每个都是坑
- 各 CLI 的安装方式不同（npm/pip/binary/curl），统一安装器本身就是一个小项目
- "初中生都能完成"：安装一个 CLI 的难度远低于调试自动安装器的 bug
- 安全风险：自动从网络下载可执行文件，需要签名验证机制
- 各 CLI 有自己的 API Key 需要配置，自动安装也无法自动配置

### 裁决：**缓行（提供脚本不自动执行）**
- 提供 `scripts/setup-executors.sh` 检测 + 提示安装命令，但不自动执行
- 文档里写清楚每个 CLI 的安装步骤和验证方法
- ADR-027 记录此决策

## 设想 5：执行中切换 CLI 模型

**设想内容**：允许在任务执行过程中动态切换 CLI 使用的模型（如从 GPT-4 切到 Claude）。

### 钢人正方
- 不同任务阶段适合不同模型（规划用大模型、编码用快模型）
- 成本控制：简单任务用便宜模型，复杂任务用贵模型

### 钢人反方
- CLI 执行体是单次进程模式（ADR-021），进程启动后模型已锁定，无法中途切换
- 中途切模型 = kill 当前进程 + 重启新进程 + 状态恢复，这会丢失执行体上下文
- "初中生都能完成"：模型选择应该在任务分配时决定，不应该在执行中动态切换

### 裁决：**采纳（任务间切换，非任务中切换）**
- 支持在任务之间的间隙切换模型（任务 A 用 GPT-4，任务 B 用 Claude）
- 通过 `.env` 的角色模型映射 + 控制台 `/api/model` 端点实现
- 不支持任务执行中切换（进程级限制）
- ADR-028 记录此决策

## 设想 6：初始化基础环境（nodejs/npm 等）

**设想内容**：在派工前自动初始化执行体所需的基础环境（安装 nodejs、npm、python 依赖等）。

### 钢人正方
- 执行体生成的代码可能需要特定运行时（如 Node.js 项目需要 npm）
- 自动初始化减少环境问题导致的失败

### 钢人反方
- 环境初始化是 DevOps 工具的职责（Docker/Devbox/Nix），不是编排器的职责
- AideanFleet 定位是"调度+审查+计量"，不是"环境管理"
- 自动安装系统级软件（nodejs）需要 root 权限，安全风险高
- "初中生都能完成"：应该假设环境已就绪，编排器只管调度

### 裁决：**缓行（Phase 3 用 Docker 镜像解决）**
- 当前假设运行环境已就绪，在 README 中列出前置依赖
- Phase 3 提供 Dockerfile 统一环境
- ADR-029 记录此决策

## 设想 7：主执行流程文档化

**设想内容**：明确并文档化主执行流程：`/fleet 启动 → UI :5000 → 接收需求 → 锁定 → 配置 Manager → 分解任务 → 组装执行体 → 监控 → 验证 → 循环`

### 钢人正方
- 当前主流程散落在 launch_core.py、intake.py、dispatcher.py、scheduler.py 中，没有一份端到端文档
- 文档化后新人（和初中生）能快速理解全局
- 流程图可以作为测试用例的验收基准

### 钢人反方
- 代码即文档，代码已经清晰描述了流程
- 文档可能与代码不同步

### 裁决：**采纳**
- 在 `.docs/03_solution/` 创建 `main-flow.md` 端到端流程文档
- 用文字流程图 + 代码引用 + 状态机联动三段式描述
- ADR-030 记录此决策
