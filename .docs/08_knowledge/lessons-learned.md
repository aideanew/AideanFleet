## 1. 认知类教训（最容易反复犯）

### L-01 「有模块」≠「分层已兑现」

> 不采纳既有未跟踪方案中的过度结论：有模块不等于全部分层已兑现。
> —— `docs/plans/2026-09-17-evidence-driven-remaining-work.md` §5.5

**教训**：代码目录里存在 `governance/`、`rel/`、`notify/` 不等于这些能力已经进入执行路径。
证据 E10/E11 明确记录了"生产调用检索未见派工前预算检查"、"生产检索未见过期检查调度与审批执行消费"。

**应用**：判断能力是否兑现时，问"生产路径上有没有真实调用点"，而不是"文件在不在"。

### L-02 Fake 验收不能推断真实执行的"从未"发生

> 不能用 Fake 验收推断真实执行"从未"发生。
> —— 同 §5.5

**教训**：替身测试通过证明的是**模板闭环与计量归属**，不是真实执行体可用。
`test_intake_to_done_integration.py` 的说明里也明确写了：不证明需求语义正确，也不覆盖 HTTP/浏览器/真实 CLI。

**应用**：验收结论必须声明证据等级（L1–L4）与覆盖边界。

### L-03 勾选框 0 ≠ 无进展

**教训**：执行方案 58 个三级任务勾选框全部为空，但 §5/§6 明确记录本轮已完成
"真实事件字段与旧格式兼容映射"、"五任务 DONE 计量归属集成测试"、"事件计量幂等（部分）"。

**应用**：进度以**证据文件与实测记录**为准，不以文件编辑状态为准。

**实证（2026-09-22，TASK-001）**：拆解 3.1.1 时发现其实现与 4/7 场景测试**早已存在且通过**
（`server.py:306-309` 四键返回、`launch_core.py:173-176` 严格布尔消费、
`tests/test_cli_launch.py::test_health_contract` 四参数化用例、
`tests/core/test_server_api.py::test_health_exact_contract_shape` 四键形状断言）。
七场景探针实测全部符合预期。真实缺口只有一个：`except Exception` 异常路径无测试断言。

**推广**：其余 57 项同样不可凭勾选框判定，须逐项实测。
见 `05_execution/tasks/TASK-001-health-contract-gap.md` §4。

### L-04 数字口径随时间演进，历史记录不得覆盖

`docs/验收清单-Phase2.md` 的修订记录展示了正确做法：

| 项 | 处理 |
| --- | --- |
| 测试总数 151 → 202 | 标注"经理复核定稿"与测量时点 |
| Claude Code `--version` 2.1.272 → 2.1.273 | 标注"本机现装…INT-04 时点属时点演进，当时探测真实有效" |
| Codex CLI 0.153.4 → 0.154.0 | 同上 |

**教训**：数字变了不等于原来的记录是错的。**要标注时点，不要改写历史。**

**应用**：验收清单记录结论时，必须带上"测量时点 + 基础提交"。

### L-05 不要根据旧 PID 直接停止进程

> 不能根据旧 PID 直接停止进程。
> —— 执行方案 §5.5

**应用**：涉及进程生命周期的操作，必须校验进程身份再动作。

### L-06 不要用不存在的 API 路径作为可执行步骤

> 不能使用尚不存在的 API 路径作为可执行步骤。
> —— 执行方案 §5.5

**应用**：写任务执行步骤前，先确认接口已在契约中定义且实现存在。

### L-07 其他会话的截图不是本轮验证

> 不得将其他会话生成的截图当作本轮验证。
> —— 执行方案 §5.3

**应用**：证据必须与本轮任务、本次执行 attempt 绑定。

### L-08 Vite build 不是类型检查的替代

> 构建和 E2E 在 W10 隔离服务就绪后运行。
> —— 执行方案 §5.3

**应用**：`vue-tsc --noEmit` 与 Vite build 是两个独立检查，都要跑。

## 2. 设计与口径类教训

### L-09 返工升级是"第 4 次"，不是"3 次"

**教训**：历史文档存在"×3 即升级"的模糊口径。
契约迁移表明确：#12 `REWORK → ASSIGNED` 条件 `rework_count <= 3`，#13 `→ ESCALATED` 条件 `rework_count > 3`。

**应用**：以 FROZEN 契约的迁移表为准，不沿用历史模糊表述。

### L-10 `seq` 唯一键 ≠ 支持多独立事件流

> 不能把当前 seq 唯一键扩展解释为支持多独立事件流。
> —— 执行方案 §6

**教训**：W6/3.6.1 的修复验证了"同一事件流重复扫描"，但跨流身份隔离、历史对账迁移、
旧格式轮转、多进程迁移**均未验证**。

**应用**：局部修复不能扩大解释为通用能力。写"部分完成"就写"部分完成"。

### L-11 历史无 `event_key` 记录没有自动回填或去重

> 历史无 event_key 记录没有自动回填或去重，首次重新导入须先对账。
> —— 执行方案 §6

**应用**：涉及数据迁移的方案必须说明"存量数据处理策略"。

### L-12 `unknown` 与 `0` 必须区分

`任务进度表字段.md`：`token` 未知时为 `NULL`，**不得填 0 冒充**。
W6/3.6.3 要求"unknown 与 0 区分，报表返回 unknown 数量"。

**教训**：把未知当零，会让成本报表系统性低估。

### L-13 plan.json 是快照，不是第二数据库

> plan.json 是人类可读快照，不是第二数据库。方向 DB → plan.json，单向不双向同步。
> —— `docs/规划总览.md` M1

**应用**：任何"JSON 反写运行态"的设计都是错的。

### L-14 轮询次数不能代替一致性证明

证据 E13：线程锁分配 seq，但"增量查询仍全文件读取"、"每秒扫描并逐事件算进度"。

**应用**：并发与性能扩展前必须先有 claim、lease 和证据隔离（这是 W9 的前置条件）。

### L-15 SQLite 事务不能回滚已追加的 JSONL

> SQLite 事务不能回滚已追加 JSONL，必须通过持久化待投递事件及可重建投影兑现一致性。
> —— `docs/规划总览.md` 材料取舍

**应用**：这正是 outbox（待投递事件）模式存在的原因。

### L-16 用户意见 ≠ 放行

证据 E04：`note` 写意见事件但不应生成执行许可；确认对象与一步语义必须可靠。

**应用**：`意见` 与 `confirm` 必须是两种不同的动作。

## 3. 安全类教训

### L-17 原始需求文件中存在明文 SMTP 凭证 ⚠️

**发现（2026-09-22 核验）**：`docs/参考/base.md` 包含明文邮件发件地址、收件地址与
SMTP 授权码。该文件是原始需求笔记，属于历史文档。

**注意**：本文件**不复述这些凭据值**。

**处理建议**：

1. 由凭证所有者确认并**轮换该授权码**（历史泄露应按已泄露处理）
2. 真值放系统环境变量，文档中只用占位符
3. `base.md` 中的明文段做脱敏（保留文件其余内容，不删除文件）

**参照**：`base.md` 的模型配置段已做过同类脱敏——
`api_key = "${FLEET_MODEL_API_KEY}" //密钥（REL-01 审计脱敏：禁止明文，真值放系统环境变量）`。

**应用**：`pyproject.toml` 依赖 `modelscope` 等，`.env` 含真实配置（已在 `.gitignore` 排除），
但历史文档中的明文不会被 `.gitignore` 保护。

### L-18 `.gitignore` 只管未跟踪文件，管不了已入库的明文

`.gitignore` 已正确排除 `.env`、`.env.bak*`、`*.pem`、`*.key`、`secrets/`。
但 `docs/参考/base.md` 是**已入库的历史文档**，`.gitignore` 对其无效。

**应用**：明文泄露必须靠脱敏 + 轮换，不能靠忽略规则。

## 4. 工作流类教训

### L-19 契约与实现必须同 owner

ADR-018 的裁决理由：

> API 契约与实现必须同 owner 才能保持"契约即实现"的同步；跨角色改服务端是 v1 契约脱节的根因之一。

**应用**：执行方案 §4.1 明确"同一文件只有一个 owner，不能同时改 `dispatcher` / `server`"。

### L-20 契约冻结不是"不许改"，是"不许覆盖"

`任务状态机.md` 明确要求：

> 如需扩展只能"新增状态/新增迁移"，不得修改既有语义。

任务字段契约 v1.1 → v1.2 的正确做法：**原位升级 + 保留版本记录 + 说明升级原因**。

### L-21 会议/讨论稿不是决策依据

`DELIVERY/` 三份讨论稿是**分析过程**，不是最终事实来源。
正式决策必须进 ADR，正式需求必须进 `02_requirements/`。

否则项目会产生大量"某次会议里说过"这种不可追溯信息。

### L-22 同名项目文档不能混用（本轮实际犯过的错）⚠️

**来源**：2026-09-22 建立 `.docs/` 文档体系时的核验

**发生了什么**：`.docs/` 初版把 `DELIVERY/` 三份讨论稿当作 AideanFleet 的需求来源与
阶段依据，包括引用"Aidean 处于建设期收官、运营期未开门、14 问 6 达标/6 部分达标/
2 结构性缺口"作为本项目的阶段定位。已推送至 GitHub 后才发现问题。

**核验事实**：

| 文档 | 实际对象 | 基线提交 |
| --- | --- | --- |
| `DELIVERY/aidean-深析讨论稿-20260922.md` | Aidean | `f1068e4` → `d17cfed` |
| `DELIVERY/启动前讨论稿-20260922-核验版.md` | AideanBot | `205c151` |
| `DELIVERY/需求复核与再设计-20260922.md` | AideanBot | `5b17da2` |
| 本仓库 | AideanFleet | `eb7a63c` |

三份文档内容涉及 Prisma model、`seed.ts`、RedFox 积分、LangBot 对接等 AideanBot 专属概念，
与本仓库（Python + FastAPI + SQLite + Vue3）无实现关系。它们是被 AideanFleet 方法论
**分析**的兄弟项目产物，而非 AideanFleet 自身的事实。

**追加（2026-09-22 复核）**：初版还把它写作"14 **关**"，原文是"14 **问**"
（`aidean-深析讨论稿（14 问全维进度…）`）。改字后该说法在本仓库文档中显得更像"本项目的关卡"，
进一步加深误读，并已被用户据此追问。已全文更正为"14 问"。

**全仓核验**：`14 关` 在 `docs/`、`reports/`、`初始设计/`、`fleet/`、`prompts/` 中出现 **0 处**。
AideanFleet **从未有过"14 关"这个概念**。

**教训**：三个名字只差一个后缀（AideanFleet / Aidean / AideanBot），
且讨论稿明确写"使用流程体系：AideanFleet 方法论层"，极易误读为"这是 AideanFleet 的文档"。
**判断文档归属必须看基线提交号与实现技术栈，不能看文件名或方法论署名。**

**应用**：

1. 引用任何既有文档前，先核对其基线提交是否属于当前仓库（`git cat-file -e <base>:<path>`）
2. 涉及"阶段定位""需求来源"的表述，必须能追溯到本项目自己的证据（E01–E20）与 ADR
3. 兄弟项目产物可以存档，但必须在 `09_archive/` 与 `document-index.md` 中显式标注对象
4. 修正记录：本次已在 8 处文档中更正归属，见 `07_release/changelog.md` 的修正条目

## 5. 新教训登记模板

```markdown
### L-NN <一句话教训>

**来源**：<文件路径 + 行号或章节>

**发生了什么**：<事实>

**教训**：<为什么错，代价是什么>

**应用**：<以后怎么避免>
```

**登记规则**：

* 必须指向可核查的来源，不接受"经验之谈"
* 写事实与后果，不写情绪
* 教训对应的规范条文更新到 `00_governance/document-standard.md` 或 `06_validation/validation-plan.md`
* 涉及决策的，同步登记 ADR
