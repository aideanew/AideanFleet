## 1. 一句话定位

**AideanFleet 是一个自主代理控制面（Control Plane），通过可插拔执行体，把自然语言需求
转化为可调度、可审查、可计量、可追溯的软件工程交付。**

更准确的架构定位（`docs/规划总览.md` M1）：

> **Multi-Agent Software Engineering Orchestrator** —— Agent 是执行资源，不是系统核心。

**项目名统一 AideanFleet**（ADR-023）。旧名 AideanCompany / AideanBot 仅作历史引用保留。

版本：`0.3.0`（`pyproject.toml`）｜ 运行方式：`fleet` CLI（`fleet.launcher.cli_start:main`）

---

## 2. 这个项目为什么存在

三个被验证过的痛点（来自执行方案的证据索引 E01–E20）：

| 痛点 | 证据 | 后果 |
| --- | --- | --- |
| 任务状态可展示，但不可追溯 | E01、E02 | 回执夸大实际动作；固定模板不能代表任意需求 |
| 证据可生成，但可能被覆盖或缺失 | E07 | 返工读到旧报告；证据写失败仍判通过 |
| 治理层存在，但未进入执行路径 | E10、E11 | 预算与审批形同虚设，不能证明真正熔断 |

**所以**：AideanFleet 的目标不是"能跑任务"，而是"能证明任务真的做完了"。

## 3. 用户与使用场景

| 用户 | 场景 |
| --- | --- |
| 开发者 / 管理者 | 提出自然语言需求，观察执行，在关键点确认，事后追溯证据 |
| AI Agent（执行体） | 作为被调度的执行资源，接收任务、返回六节报告与证据 |
| 审查角色 | 独立于执行身份，审查交付物并给出 verdict |

**双入口**（`docs/参考/base.md`）：

```text
方式一：CLI 引导启动 → Hermes 接收指令
方式二：Hermes 直接接收指令
```

无论哪种入口，首先打开网页控制端，由网页动态控制（ADR-017：UI = 控制台 = 5000）。

```text
[总览, 对话, 模型, 角色, 执行体, 拓展, 消息]
```

| 页面 | 内容 |
| --- | --- |

### Out of Scope（本仓库不承诺）

| 不做的 | 原因 |
| --- | --- |
| 消息中间件、ORM、微服务化 | 本轮前提明确排除（执行方案 §1） |
| 核心代码依赖前端框架 | ADR-016 硬边界 |
| 交互式 CLI 派工 | ADR-021：派工默认单次、非交互 |
| 真实外部依赖的性能承诺 | 未验证项明确不在发布承诺内（G4 出口条件） |
| 多租户 / SaaS 化 | 单用户本地控制面定位 |

## 5. 成功指标

### 5.1 交付可信度（核心指标）

| 指标 | 判定 |
| --- | --- |
| 需求 → 交付可双向追溯 | 任一节点可向前追溯到需求，向后追溯到证据 |
| 完成有证据 | Done = Implementation + Acceptance + Verification + Evidence |
| 证据不被覆盖 | 每轮 attempt 独立证据，首轮证据保持不变 |
| 验收不被绕过 | 机器门执行完毕才进 REVIEWING；证据写失败关闭验收 |

### 5.2 治理有效性

| 指标 | 判定 |
| --- | --- |
| 计量幂等 | 同事件扫描两次总量不变（W6/3.6.1，当前部分完成） |
| 预算真正熔断 | 余额不足时 adapter 未调用（E10，未验证） |
| 审批绑定具体动作 | 批准只放行对应动作一次，拒绝/过期不放行（E11，未验证） |
| 计量归属可对账 | 项目/任务/角色/模型四维归属 |

### 5.3 一致性

| 指标 | 判定 |
| --- | --- |
| 唯一调度者 | 同项目重复启动只存在一个有效调度者 |
| 原子领取 | 同任务并发请求只获得一个 claim |
| 事件可对账 | 故障点中断后 DB 事件与 JSONL 可逐条对账 |
| 计划可重建 | 丢失快照可仅从 DB 重建完整三级顺序及状态 |

### 5.4 核验口径

执行方案 §5.5 确立的取证原则：

> **只信实测，不信自述。**

具体表述：不采纳既有未跟踪方案中的过度结论——
有模块不等于全部分层已兑现；Fake 验收不能推断真实执行"从未"发生；
不能用尚不存在的 API 路径作为可执行步骤；不能根据旧 PID 直接停止进程。

来源：[`docs/plans/2026-09-17-evidence-driven-remaining-work.md`](../../docs/plans/2026-09-17-evidence-driven-remaining-work.md) §5.5

## 6. 阶段定位

来源：执行方案 §3 的工作包分层与 §4.3 的分阶段出口（G0–G4）。

当前处于**建设期收尾**：控制面、前端、治理层、集成与首次发布（REL-01）已交付，
但 W1–W10 共 58 个行为项仍未完成，证据与治理尚未进入执行路径（E07/E10/E11）。

当前目标（Phase 2）是**正确性优先**：先收敛执行所有权与数据一致性，
再补需求决策与治理闭环，最后做有界并发与性能优化。

⚠️ 说明：`DELIVERY/` 下"Aidean 处于建设期收官、运营期未开门"的 14 问判定
属于 Aidean/AideanBot 兄弟项目，**不构成本项目的阶段依据**。本项目的阶段划分
完全来自执行方案自身的 W1–W10 与 G0–G4。

详见 [`../04_planning/roadmap.md`](../04_planning/roadmap.md)。
