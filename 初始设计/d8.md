那么既然能做到多角色合作编码开发的工作，同样也能做团队自媒体创作的工作吧，同理其他工作只要是重复性的、分工明确的，大部分都能做出来。

那么该项目设计是否能完善呢

-----

可以，而且这会让项目的定位发生一次很重要的升级：你现在设计的其实不应该叫“多 Agent 编码系统”，而应该进一步抽象成“可配置的 AI 团队工作流执行系统”。

编码开发只是第一个、也是最适合验证它的垂直场景。

比如自媒体团队完全可以映射：

```text
软件开发                    自媒体

需求/Task Pack              选题 Brief
Planner                     主编/策划
后端工程师                   资料研究员
前端工程师                   文案作者
测试工程师                   事实核查员
Manager                     主编/审核
pytest/build                事实检查/敏感词/格式检查
Git diff                    稿件版本 diff
截图/测试日志                引用来源/素材/数据
report.html                 发布包/审核报告
Git worktree                Draft Workspace
Claude/Codex/OpenCode        各种文本/图片/视频 Agent
```

再往外推，客服、SEO、市场研究、竞品监控、销售线索整理、运营日报、数据分析、财务资料整理等，本质上都可能落入同一个模型：

```text
输入
 ↓
工作契约
 ↓
任务分解
 ↓
专业角色执行
 ↓
工具调用
 ↓
产物
 ↓
机器检查
 ↓
AI 审核
 ↓
返工/恢复
 ↓
最终交付
```

所以答案不是简单的“把现在 Coding Fleet 加几个角色”。我建议趁还没写太多代码，把底层抽象再提升一级。

一、把 Agent Fleet 拆成“通用内核 + Domain Pack”

现在一些设计实际上偷偷写死了 Coding：

```text
git worktree
allowed_paths
ports
pytest
CLI coding agent
diff
build
```

这些不应该属于核心 Kernel，而应该属于 Software Development Domain。

真正通用的 Kernel 应该只有：

```text
              AI Team Runtime
                    │
        ┌───────────┼───────────┐
        │           │           │
     Workflow     Worker     Resource
      Engine      Runtime      Manager
        │           │           │
        ├──────── Event Bus ─────┤
        │                        │
   Policy Engine            Artifact Store
        │                        │
        └──────── Gate Engine ───┘
                    │
                 Report
```

然后：

```text
                    Kernel
                      │
        ┌─────────────┼──────────────┐
        │             │              │
   Coding Pack   Media Pack     Research Pack
        │             │              │
 Claude Code     Writer Agent    Search Agent
 Codex           Image Agent     Browser Agent
 Git             Video Agent     Python
 pytest          Publisher       Database
 Browser         SEO Checker     Spreadsheet
```

这会比继续围绕 `bases/claude_adapter.py` 设计整个系统有更长的生命周期。

二、最重要的抽象要从 Backend 升级成 Worker

当前：

```text
BaseAdapter
 ├ ClaudeCodeAdapter
 ├ CodexAdapter
 └ OpenCodeAdapter
```

仍然太偏 Coding。

未来很可能需要：

```text
Worker
├── AgentWorker
│   ├── ClaudeCode
│   ├── Codex
│   ├── OpenCode
│   ├── OpenAI API
│   └── Claude API
│
├── ToolWorker
│   ├── Python
│   ├── Shell
│   ├── Browser
│   └── FFmpeg
│
├── ServiceWorker
│   ├── ImageGenerator
│   ├── TTS
│   ├── Search
│   └── Publisher
│
└── HumanWorker
    └── Approval
```

这是一个很关键的设计。

因为真正团队里的“员工”并不一定都是 LLM。

比如自媒体流程：

```text
研究员 Agent
   ↓
作者 Agent
   ↓
事实核查 Agent
   ↓
敏感词程序
   ↓
图片生成 Service
   ↓
FFmpeg
   ↓
主编 Agent
   ↓
Human Approval
   ↓
平台发布 API
```

如果 Kernel 只认 Claude/Codex，就会很快遇到第二次重构。

三、Task Pack 也应该升级为通用 Job Spec

Coding：

```yaml
goal: 修复登录功能

inputs:
  - source_code

outputs:
  - patch
  - test_report

acceptance:
  - pytest
  - build
```

自媒体：

```yaml
goal: 制作一期 AI 行业周报

inputs:
  - topic: AI Agent
  - sources: [...]
  - brand_guide: brand.md

outputs:
  - article
  - cover_image
  - social_posts

acceptance:
  - citations_valid
  - no_duplicate
  - style_match
  - forbidden_words_check
```

所以 Kernel 应该认识的是：

```text
Job
Task
Input
Output
Artifact
Constraint
Resource
Gate
Evidence
Dependency
Budget
```

而不是：

```text
Repository
Port
Git
pytest
```

后者全部是插件。

四、Gate Engine 会成为整个项目最有价值的组件之一

你之前 Coding 场景里的核心思想：

“员工说自己完成了，不算完成。”

这个原则在所有领域都成立。

自媒体也一样：

作者说：

```text
所有数据都有来源。
```

不算 Evidence。

系统应该验证：

```text
claim
 ↓
citation
 ↓
URL
 ↓
retrieve
 ↓
source exists?
 ↓
source supports claim?
```

所以 Gate 应该插件化：

```text
Gate
├── Coding
│   ├── CommandGate
│   ├── TestGate
│   ├── PortGate
│   ├── DiffGate
│   └── BuildGate
│
├── Media
│   ├── CitationGate
│   ├── PlagiarismGate
│   ├── BrandGate
│   ├── SensitiveWordGate
│   └── AssetGate
│
├── Research
│   ├── SourceGate
│   ├── FreshnessGate
│   ├── CrossCheckGate
│   └── CalculationGate
│
└── Common
    ├── SchemaGate
    ├── BudgetGate
    └── HumanApprovalGate
```

甚至可以直接定义：

```python
class Gate(Protocol):
    async def verify(
        self,
        task: Task,
        artifacts: list[Artifact],
        context: RunContext,
    ) -> GateResult:
        ...
```

五、Skills 也可以真正成为公司知识库

你目前：

```text
skills/
  backend-test/
  playwright/
  ruff-mypy/
```

未来：

```text
skills/
├── coding/
│   ├── backend-test
│   └── frontend-e2e
│
├── media/
│   ├── xiaohongshu-style
│   ├── wechat-article
│   ├── seo
│   └── video-script
│
├── research/
│   ├── fact-check
│   └── competitor-analysis
│
└── company/
    ├── brand-guide
    ├── security-policy
    └── approval-policy
```

此时 Skill 的意义就不只是 prompt 片段，而是：

```text
Skill =
Knowledge
+ Procedure
+ Tools
+ Permissions
+ Gates
+ Version
```

例如：

```yaml
name: wechat-article
version: 3

requires:
  tools:
    - web_search

procedure:
  - research
  - outline
  - draft
  - fact_check
  - polish

gates:
  - citation_check
  - forbidden_words
  - brand_style

  - article.md
  - sources.json
```

这个模型会比简单的 SKILL.md 强很多。

六、Manager 也不要固化成一个“管理员”

甚至应该取消 Kernel 里的 Manager 概念。

因为不同团队的管理关系完全不同：

```text
软件团队：
Developer → Tester → Tech Lead

自媒体：
Researcher → Writer → Fact Checker → Editor

研究：
Researcher A ─┐
Researcher B ─┼→ Synthesizer → Reviewer
Researcher C ─┘

客服：
Classifier → Specialist → QA
                       ↓
                 Human Escalation
```

所以“管理员”应该只是 Workflow 里的一个 Role。

Kernel 只认识：

```text
Role
Task
Dependency
Gate
Policy
```

这样支持：

```text
DAG
Sequential
Parallel
Map/Reduce
Review Loop
Approval
Conditional Branch
Retry
Escalation
```

这时候系统就真正通用了。

七、建议重新设计目录边界

如果项目现在还在早期，我会直接改成：

```text
ai_fleet/
├── core/
│   ├── workflow/
│   ├── scheduler/
│   ├── events/
│   ├── state/
│   ├── policy/
│   ├── artifacts/
│   ├── evidence/
│   ├── gates/
│   └── resources/
│
├── workers/
│   ├── agents/
│   │   ├── claude_code.py
│   │   ├── codex.py
│   │   ├── opencode.py
│   │   └── pi.py
│   ├── shell.py
│   ├── python.py
│   ├── browser.py
│   └── human.py
│
├── domains/
│   ├── coding/
│   ├── media/
│   └── research/
│
├── skills/
```

关键依赖方向必须固定：

```text

```

也就是说 Kernel 永远不知道“Claude Code”“微信公众号”“pytest”是什么。

八、fleet.yaml 也可以从“员工配置”升级成真正的组织配置

比如：

```yaml
organization:
  name: My AI Studio

roles:
  researcher:
    worker:
      type: agent
      backend: opencode
      model: qwen
    skills:
      - web-research

  writer:
    worker:
      type: agent
      backend: claude
      model: sonnet
    skills:
      - brand-writing

  editor:
    worker:
      type: agent
      backend: codex
      model: gpt-5
    skills:
      - fact-check
      - editorial-review

resources:
  browser:
    capacity: 2

  expensive_model:
    capacity: 1

budgets:
  daily_usd: 30
  max_parallel: 4
```

然后 Workflow 独立：

```yaml
name: weekly-ai-news

tasks:
  research:
    role: researcher

  draft:
    role: writer
    depends_on: [research]

  check:
    role: editor
    depends_on: [draft]

  revise:
    role: writer
    when: check.failed

  publish:
    worker: publisher
    depends_on: [check]
    gates:
      - human_approval
```

这就开始接近“AI 组织运行时”了。

九、但是有一个边界必须守住

“重复性、分工明确的工作大部分可以做”这个方向是成立的，但不要进一步推导成：

“所有白领工作都可以用一个通用 Agent Workflow 自动化。”

不同领域真正困难的是 Gate。

代码很幸运：

```text
pytest -> exit 0
```

是非常强的验证器。

文章好不好、研究结论是否可靠、营销内容是否符合品牌、客服回复是否会产生法律风险，就没这么容易机器判定。

因此越往 Coding 之外扩展：

```text
Machine-verifiable
        ↓
AI-verifiable
        ↓
Human-verifiable
```

后两者比例会越来越高。

所以 Kernel 从第一天就应该支持：

```yaml
gate:
  type: human_approval
  risk: high
```

不要以“100% 无人值守”为系统设计目标。更好的目标是：

“能自动化的自动化，不能可靠自动判定的工作自动升级。”

十、这样项目最终可以分三层发展

第一阶段不用改变：Coding Fleet。

```text
Task Pack
→ 多 Coding Agent
→ Worktree
→ Test
→ Evidence
→ Report
```

把核心引擎跑稳定。

第二阶段验证通用性：Media Fleet。

做一个真实流程：

```text
选题
→ 搜索
→ 多研究员并行
→ 汇总资料
→ 写稿
→ Fact Check
→ 配图
→ Editor
→ Human Approval
→ 发布包
```

如果 Coding 和 Media 都能用同一个 Kernel、不修改 core，那么抽象基本成功。

第三阶段才可以考虑更大的：

```text
                AI Organization Runtime

                     Workflow
                        │
       ┌────────────────┼────────────────┐
       │                │                │
   Engineering        Media          Operations
       │                │                │
 Claude/Codex       Writer/Image     Browser/CRM
       │                │                │
       └──────────── Core Runtime ───────┘
                        │
          State / Event / Artifact
          Policy / Budget / Evidence
          Resource / Gate / Approval
```

这时你最早 d0/d4 里的 “One-Company” 愿景才有一个比较扎实的底座。

所以，我认为项目不仅“能完善”，而且现在恰好是完善架构的最佳时间点。最值得做的不是继续增加 A/B/C 员工，而是完成一次抽象升级：

```text
Coding Agent Orchestrator
          ↓
Agent Fleet
          ↓
AI Workflow Runtime
          ↓
AI Organization Runtime
```

但开发顺序不要跟着愿景膨胀。产品愿景可以是最后一层，MVP 仍然只实现第一层。设计 Kernel 时不写死 Coding，第一版只交付 Coding Domain；然后拿自媒体 Domain 做第二个“架构单元测试”。

如果同一套 core 最终能够同时不打补丁地运行：

```text
软件需求 → 代码 → 测试 → 验收
```

和：

```text
选题 → 调研 → 写稿 → 核查 → 审稿 → 发布
```

那么这个项目的核心架构基本就真正立住了。
