综合你目前给我的两批材料和最初需求，我会把技术基线固定为：

```text
Agent Fleet = 自研薄 Control Plane
            + 可插拔 Coding Agent Runtime
            + 确定性工程执行层
            + Evidence-first 验收体系

Coding Agent Runtime:
Claude Code / Codex / OpenCode / pi / future...

Control Plane:
TaskPack
→ Planner/DAG
→ Scheduler
→ Workspace/Resource Lease
→ Adapter
→ Event Bus
→ Recovery Policy
→ Machine Gate
→ Semantic Verifier
→ Report
```

其中最值得保留的新观点，是“pi 作为第四个 Adapter，而不是 Orchestrator”。这个抽象也意味着以后再出现新的 coding agent，只需要：

```text
fleet.yaml
     │
BackendRegistry
     │
     ├── ClaudeCodeAdapter
     ├── CodexAdapter
     ├── OpenCodeAdapter
     ├── PiAdapter
     └── FutureAdapter
```

Control Plane 完全不需要知道 worker 内部怎么思考。

不过这份资料里还有几个点，我会继续做工程化修正。

第一，“Machine Gate 先于 Manager”应该成为硬架构规则，而不只是优化。例如：

```text
Worker 完成
   ↓
Collect Evidence
   ↓
Diff Gate
   ↓
Path Gate
   ↓
Port Gate
   ↓
Command/Test Gate
   ↓
Artifact Contract Gate
   ↓
         PASS
           ↓
Semantic Verifier
           ↓
Merge Gate
```

Manager/Verifier 不应该有权把一个 `pytest exit_code=1` 解释成 PASS。LLM 可以解释失败原因，不能篡改事实层结果。

第二，端口验证也不能简单等同于 `netstat`。生产实现需要 Resource Lease：

```text
3333
 ├── owner_run_id
 ├── owner_task_id
 ├── pid/process-group
 ├── acquired_at
 └── release policy
```

系统只能清理自己拥有的 process tree。发现外部 PID 占 3333，应报告：

```text
RESOURCE_BLOCKED(PORT_3333)
```

而不是直接 kill。

第三，“Worktree 解决 A/B 同改 backend/**”只解决隔离，不解决最终冲突。因此调度器还需要 `write_set/read_set` 概念。Task Pack 最好支持：

```yaml
workspace:
  read:
    - backend/**
    - docs/**
  write:
    - backend/auth/**
  deny:
    - frontend/**
    - .env*

resources:
  exclusive:
    - port:3333
```

Scheduler 可以在运行前就发现：

```text
A.write ∩ B.write != ∅
```

然后选择串行，而不是等 merge 时才发现。

第四，参考材料里提到“重新 build_prompt，带 history”和另一处“重试清空 history”其实需要合并成更精确的机制：不要携带聊天 history，携带结构化 Retry Context。

例如：

```yaml
retry_context:
  previous_attempt: 2
  failure:
    type: TEST_FAILURE
    evidence: EV-CMD-018
  previous_diff: EV-DIFF-007
  instruction: "只修复上述失败，不扩大任务范围"
```

这比把几十 KB stdout 和上一轮 Agent 对话重新塞进去稳定很多。

第五，我会把 Error Bus 扩展成统一 Event Bus，因为正常事件和错误事件实际上应该走同一套审计管道：

```text
RUN_CREATED
TASK_READY
WORKER_STARTED
AGENT_EVENT
COMMAND_STARTED
COMMAND_FINISHED
FILE_CHANGED
RESOURCE_ACQUIRED
RATE_LIMITED
RETRY_SCHEDULED
GATE_FAILED
TASK_SUCCEEDED
...
```

全部 append-only。SQLite 则保存当前投影状态。

因此：

```text
events.jsonl = What happened?
SQLite       = Where are we now?
artifacts/   = Where is the evidence?
```

这三个职责不要混。

还有一个重要升级：最终状态不应该只有 DONE/FAIL。建议从第一版就定义：

```text
PENDING
READY
RUNNING
VERIFYING
RETRY_WAIT
SUCCEEDED
FAILED
BLOCKED
ESCALATED
CANCELLED
```

尤其 `BLOCKED` 和 `FAILED` 必须区分。比如 3333 被用户自己的服务占着，不是 Agent “执行失败”。

至于 OpenClaw/Hermes/pi 这组判断，我接受其架构结论，但涉及它们“截至 2026-09 的具体功能、issue 状态、CLI 参数”的陈述，在真正编码前仍应以各项目当前官方文档和本地 `--help/--version` 为准。第三方比较文章不能成为 Adapter 契约。

所以 Adapter 最终应该带 capability discovery：

```python
Capabilities(
    streaming=True,
    structured_output=True,
    resume_session=False,
    mcp=True,
    native_skills=True,
    sandbox=True,
    usage_reporting=True,
)
```

而不是假设四个 CLI 能力完全一样。

到现在为止，我认为可以冻结几项 ADR（架构决策），后续不再反复选型：

- ADR-001：不用 MetaGPT/CrewAI/LangGraph/Mastra/OpenClaw 做核心 Orchestrator。
- ADR-002：Python 3.11+ 自研薄 Control Plane。
- ADR-003：Claude Code / Codex / OpenCode / pi 全部视为 Worker Backend。
- ADR-004：CLI 差异只能存在于 Adapter 层。
- ADR-005：确定性恢复由 Policy Engine 执行，Manager 不处理机械重试。
- ADR-006：Machine Gate 权威高于 Agent 自述。
- ADR-007：Evidence immutable/raw-first，report.html 从事实数据生成。
- ADR-008：每个并发写任务使用独立 git worktree；共享资源使用 Lease。
- ADR-009：SQLite 存状态，JSONL 存事件，filesystem 存 artifact/evidence。
- ADR-010：MVP UI 使用 Streamlit，但核心代码不得依赖 Streamlit。
- ADR-011：MCP 是未来工具协议，不拿 MCP 代替内部 Scheduler/Event Bus。
- ADR-012：OpenClaw 保留给未来运营/客服/常驻 Agent 层，不进入当前开发工厂核心依赖。

最终整个系统其实可以浓缩成一句比较准确的定义：

```text
Agent Fleet 是一个针对 Coding Agent 的、
契约驱动（TaskPack）、
事件溯源（Event Log）、
资源隔离（Worktree/Lease）、
策略恢复（Policy Engine）、
证据验收（Machine Gate + Verifier）
的轻量级执行控制面。
```

这比“多个 AI 员工加一个管理员”更适合作为真正的软件架构定义。

基于现在这些资料，我认为下一阶段已经不值得继续泛泛调研“到底用哪个多 Agent 框架”。真正需要设计清楚的是 `fleet.schema.json`、`taskpack.schema.json`、`Event`、`Evidence`、`BackendAdapter`、`State Machine`、`Gate` 这几个稳定协议。一旦这几个协议冻结，Claude Code、Codex、OpenCode、pi 甚至将来的其他 coding agent 都只是外围插件，而不是系统地基。
